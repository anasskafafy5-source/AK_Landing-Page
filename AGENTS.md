# AKS Landing Page — Codex Project Instructions

## Project Overview

This project is a premium one-page SaaS landing page for **AKS**, an AI-powered workspace designed to help companies organize their work, automate repetitive processes, manage teams, and make better decisions from one unified platform.

The project is primarily a portfolio showcase. It should demonstrate strong frontend development skills, modern visual design, responsive layout, clean component architecture, and polished scroll-based animation.

The final result should feel like a real modern B2B SaaS product, not a generic template or an overdecorated AI-generated concept.

## Product Description

AKS is an intelligent workspace for modern companies and teams.

The platform helps businesses:

- Organize projects, tasks, and team workflows.
- Automate repetitive operations.
- Prioritize tasks using AI.
- Summarize meetings and extract action items.
- Track team performance and productivity.
- Generate intelligent insights and reports.
- Keep collaboration and information in one place.

The landing page should communicate that AKS reduces scattered work, saves time, improves visibility, and helps teams focus on important work.

## Target Audience

The landing page is aimed at:

- Startups and growing companies.
- Small and medium-sized businesses.
- Operations managers.
- Project managers.
- Team leaders.
- Remote and hybrid teams.
- Companies looking to automate and organize their internal work.

The tone should feel professional, confident, modern, and clear. Avoid excessive technical language in customer-facing content.

## Technology Stack

Use the existing project setup and follow these technologies:

- Next.js with the App Router.
- React.
- Tailwind CSS v4.
- Motion for React from `motion/react`.
- `next/image` for images.
- Lucide React for interface icons when needed.

Do not introduce unnecessary dependencies.

## Tailwind and Color Rules

All project colors are already defined as theme variables inside `globals.css` using Tailwind CSS v4 `@theme` variables.

Always use the existing semantic Tailwind classes instead of hardcoded colors.

Examples:

```jsx
className="bg-background text-text"
className="bg-surface border-border"
className="bg-primary hover:bg-primary-hover"
className="text-text-secondary"
className="text-muted"
className="text-accent"
```

Do not use arbitrary hex values such as:

```jsx
className="bg-[#040816]"
```

Do not redefine the color system inside components.

### Brand Color Meaning

- Dark background colors represent the product environment and premium visual style.
- Blue is the primary product and action color.
- Purple is reserved for AI-related elements and special highlights.
- Green, orange, and red are only for status feedback.

### Purple Usage

Purple must be used sparingly and intentionally for:

- AI-powered badges.
- AI Assistant elements.
- AI insights.
- AI automation features.
- Small gradient highlights.
- A subtle glow around an AI-specific interface element.
- The `Most Popular` pricing badge when appropriate.

Do not use purple across every card or section.

## Visual Direction

The design should feel:

- Premium.
- Modern.
- Dark.
- Clean.
- Spacious.
- Technology-focused.
- Suitable for a real B2B SaaS company.

Use:

- Dark blue-black backgrounds instead of pure black.
- Blue as the main accent.

- Large, readable typography.
- Clear spacing and hierarchy.
- Thin borders.
- Soft gradients.

## Data and Content Organization

Static landing-page content must be stored in the root-level `data/` directory, outside `app/`, `components/`, and any `src/` directory.

Do not create:

```text
src/data/
```

Use:

```text
data/
```

The `data/` directory is responsible for static content such as:

- Navigation links.
- Hero content.
- Company or partner names.
- Services.
- Product showcase items.
- About metrics.
- Testimonials.
- Pricing plans.
- FAQ items.
- Contact information.
- Footer link groups when needed.

Prefer one data file per major section when the amount of content justifies it.

Example:

```js
// data/services.js

export const services = [
  {
    id: "workflow-automation",
    title: "Workflow Automation",
    description: "Automate repetitive processes and keep work moving.",
    image: "/images/services/workflow-automation.webp",
  },
];
```

Components should import data from the root `data/` directory instead of embedding large content arrays inside component files.

Example:

```js
import { services } from "@/data/services";
```

Keep small one-off strings inside a component only when extracting them would reduce clarity rather than improve it.

Do not place presentation logic, Motion values, JSX, React components, or browser-specific logic inside the `data/` directory.

## Image and Asset Organization

All images must be stored inside `public/`.

Use this base directory:

```text
public/images/
```

When a section uses multiple images, create a folder named after that section.

Examples:

```text
public/images/hero/
public/images/services/
public/images/showcase/
public/images/testimonials/
```

When a section requires only one simple image, it may still use a section folder for consistency, but do not create unnecessary folder nesting.

Shared assets that are used in several sections should be stored inside:

```text
public/images/shared/
```

Examples of shared assets:

- Brand logo.
- General decorative shapes.
- Shared avatars.
- Common product interface assets.

Do not import local image files from the root `data/` directory.

Data files should reference public image paths as strings:

```js
image: "/images/hero/dashboard.webp"
```

Use `next/image` to render meaningful images.

Use clear, descriptive file names:

```text
dashboard-overview.webp
ai-assistant-card.webp
workflow-automation.webp
team-analytics.webp
```

Avoid unclear names such as:

```text
image1.png
pic-final.png
new-image-2.png
```

Prefer optimized formats such as WebP or AVIF when practical.

## Section Requirements

### Navbar

- Fixed or sticky at the top.
- Transparent or minimal at the top of the page.
- Add a dark translucent background, blur, and subtle border after scrolling.
- Include the AKS logo, navigation links, and a clear primary CTA.
- Navigation links should scroll smoothly to page sections.
- Keep the mobile navigation accessible and simple.

### Hero

The Hero is one of the two main visual moments of the page.

It should contain:

- A small AI-related badge.
- A strong headline explaining the product value.
- A supporting description.
- A primary CTA.
- A secondary CTA such as viewing the product or exploring services.
- A main dashboard or product interface visual.
- Two or three small floating product cards around the dashboard.

The Hero animation should make the interface feel as if it is being assembled:

1. The badge appears.
2. The heading and supporting text move toward their final position.
3. Buttons appear afterward.
4. The dashboard enters using opacity, upward movement, and slight scale.
5. Floating cards enter from different nearby directions.
6. After settling, floating cards may use very subtle continuous movement.

Do not use more than three floating cards.

### Trusted By

The exact visual style can be decided during implementation.

Possible directions:

- A clean static logo row.
- A slow horizontal marquee.
- A responsive logo grid.

The animation must remain subtle and should not compete with the Hero or Services sections.

### Our Services

This is the second major visual moment.

The user should feel that scrolling continues naturally while the content inside the section changes.

Preferred implementation:

- A tall section with a sticky full-screen or near-full-screen inner container.
- Services appear one after another based on scroll progress.
- The left side can show service number, title, and description.
- The right side can show a related visual or interface card.
- After the final service is displayed, the sticky behavior ends naturally and scrolling continues to the next section.

Potential services:

- Workflow Automation.
- AI Task Prioritization.
- Team Analytics.
- Meeting Summaries.

Use `useScroll` and `useTransform` when appropriate. Do not trap scrolling or create confusing scroll behavior.

### Product Showcase

Show the product through several separate showcase rows.

Recommended pattern:

```text
Text / Product UI
Product UI / Text
Text / Product UI
```

Each row should reveal as it enters the viewport:

- Text uses a subtle horizontal or upward reveal.
- Product UI uses opacity and slight scale.
- Small elements inside the product mockup can appear afterward using staggered animation.

Avoid adding another heavy sticky-scroll interaction immediately after the Services section.

### About AKS

Use a strong brand statement instead of a generic company biography.

The main statement can reveal word by word or line by line.

Example direction:

> We build intelligent systems that help teams focus, collaborate, and move faster.

Recommended animation:

- Reveal words or short lines sequentially.
- Use small upward movement, opacity, and optional light blur.
- Do not animate individual letters.

Supporting metrics or facts can appear afterward with simple fade-up animation.

### Testimonials

- Use three or more testimonial cards.
- Cards should move upward and appear one after another.
- Use a consistent motion direction for all cards.
- Keep quotes believable and relevant to the product problems.
- Avoid exaggerated marketing claims.

### Pricing

- Keep the animation simple.
- Pricing cards appear using a small stagger.
- The featured plan can be slightly elevated.
- Use purple only for a special badge such as `Most Popular`.
- Avoid large scale effects that move the pricing layout.

### FAQ

- Use a clean accessible accordion.
- Use Motion layout animation for opening and closing answers.
- Rotate the indicator icon smoothly.
- Keep scroll entrance animation minimal or omit it.

### CTA

- Create a strong final conversion section.
- Use a subtle blue gradient or glow.
- Purple may appear only as a small AI-related highlight.
- Include one clear primary action.

### Contact

- Keep this section functional and simple.
- Use a clean contact form or basic contact details.
- Use subtle fade-up animation only.
- Inputs should use existing theme colors and clear focus states.

### Footer

- Keep the Footer simple and mostly static.
- Include the AKS logo, navigation links, legal links, and social links.
- Do not add noticeable decorative animation.

## Motion System

Use Motion consistently. The website should have a unified motion language.

Recommended base easing:

```js
const smoothEase = [0.22, 1, 0.36, 1];
```

Recommended reveal movement:

```js
const fadeUp = {
  hidden: {
    opacity: 0,
    y: 32,
  },
  visible: {
    opacity: 1,
    y: 0,
    transition: {
      duration: 0.6,
      ease: [0.22, 1, 0.36, 1],
    },
  },
};
```

Recommended stagger range:

```text
0.08s to 0.16s
```

General rules:

- Prefer transforms and opacity for smooth performance.
- Avoid animating layout-heavy properties unnecessarily.
- Scroll animation must support the content, not distract from it.
- Use strong animation mainly in the Hero and Services sections.
- Keep the rest of the page controlled and subtle.
- Use `viewport={{ once: true }}` for most reveal animations.
- Respect reduced-motion preferences.
- Disable or simplify continuous and scroll-linked animations when reduced motion is enabled.
- Avoid long animation delays that make the interface feel slow.

### Shared Motion Values

If the same animation values or variants are used by several sections, store them in:

```text
constants/animations.js
```

Examples:

- Shared easing values.
- Fade-up variants.
- Stagger containers.
- Reduced-motion fallbacks.

Do not move a motion configuration into `constants/animations.js` when it is unique to one component and easier to understand locally.

Do not put Motion configuration inside the `data/` directory.

## Responsive Design

The landing page must work well on:

- Mobile.
- Tablet.
- Laptop.
- Large desktop screens.

Requirements:

- Build mobile-first.
- Avoid horizontal overflow.
- Ensure dashboard mockups remain readable.
- Reposition or hide decorative floating cards when space is limited.
- Sticky scroll sections must have a simpler mobile experience if the desktop interaction does not translate well.
- Keep buttons large enough to tap.
- Preserve clear spacing and content hierarchy at all breakpoints.

## Accessibility

- Use semantic HTML.
- Maintain proper heading order.
- Add useful alt text to meaningful images.
- Decorative images should use empty alt text.
- Buttons and links must be keyboard accessible.
- The FAQ must expose accessible expanded and collapsed states.
- Form inputs must have visible labels.
- Maintain sufficient contrast.
- Respect `prefers-reduced-motion`.

## Next.js Best Practices

- Keep components as Server Components by default.
- Add `"use client"` only to components that need state, browser APIs, event handlers, or Motion hooks.
- Keep client boundaries small.
- Use `next/image` correctly with explicit dimensions or `fill` and a stable parent.
- Define meaningful page metadata in `layout.jsx` or the relevant page.
- Avoid unnecessary runtime data fetching because the page is primarily static.
- Store static content in the root-level `data/` directory.
- Store all image assets under `public/images/`.
- Organize multiple section images inside `public/images/<section-name>/`.
- Reference public images with paths such as `/images/hero/dashboard.webp`.
- Avoid placing the entire landing page in one client component.
- Do not place static content files inside `src/data`.
- Do not import images from arbitrary component directories when they belong in `public/images`.

## Code Quality Rules

- Write clean, readable, maintainable code.
- Use descriptive component and variable names.
- Avoid giant components.
- Avoid unnecessary abstractions.
- Reuse shared layout and reveal patterns when repetition is clear.
- Do not duplicate long Tailwind class strings when a small reusable component is clearly beneficial.
- Do not create a component for every tiny element.
- Keep content separate from presentation when practical.
- Use JavaScript unless the existing project is already configured for TypeScript.
- Preserve the existing project conventions.
- Components should focus on layout, behavior, and presentation.
- Root-level data files should focus on static content only.
- Public image folders should follow clear section-based naming.
- Do not hardcode large arrays of services, testimonials, plans, or FAQ items inside section components.
- Do not create a single giant `landing-page-data.js` file when section-specific files are easier to maintain.

## Import Rules

Use the configured `@/` alias when available.

Examples:

```js
import { services } from "@/data/services";
import { pricingPlans } from "@/data/pricing";
import Container from "@/components/ui/Container";
```

Do not use deeply nested relative imports when an alias is already configured.

Avoid circular dependencies between:

- `components/`
- `data/`
- `constants/`
- `lib/`

The `data/` directory must not import React components.

## Important Constraints

- Do not hardcode colors when matching semantic variables already available in `globals.css`.
- Do not replace the existing Tailwind theme variables.
- Do not add a second styling system.
- Do not use animation libraries other than Motion unless explicitly requested.
- Do not copy an existing landing-page template.
- Do not make the interface look like a generic AI-generated design.
- Do not overuse purple, glow, glass effects, gradients, or floating elements.
- Do not implement a backend unless explicitly requested.
- Do not create `src/data`.
- Do not store landing-page images in the `data/` directory.
- Do not store multiple unrelated assets in one unorganized public folder.
- Do not hardcode image paths repeatedly when they belong to section data objects.
- Do not create unnecessary folder nesting.

## Workflow for Codex

Before making large changes:

1. Inspect the current project structure.
2. Read `AGENTS.md`.
3. Read `globals.css` and identify the existing theme variable names.
4. Inspect the root-level `data/` directory for existing content.
5. Inspect `public/images/` for available assets.
6. Check whether the current section already has an image folder.
7. Reuse existing components and conventions where appropriate.
8. Briefly state which files will be changed.
9. Implement one section or clear task at a time.
10. Keep responsive behavior and reduced motion in mind during implementation.
11. Run lint and build checks after meaningful changes.
12. Report any unresolved warnings or limitations honestly.

Before implementing a section:

1. Check whether its content already exists inside `data/`.
2. Check whether its images already exist inside `public/images/<section-name>/`.
3. Reuse existing UI components before creating new ones.
4. Do not hardcode content inside components when it belongs in the data layer.
5. Keep presentation, content, and assets separated.
6. Do not invent missing images when the section is expected to use supplied assets.
7. Use a restrained placeholder only when explicitly allowed.

When adding new static content:

1. Add it to the appropriate file inside the root `data/` directory.
2. Create a new data file only when it improves organization.
3. Reference any related image using its `/images/...` public path.
4. Keep the data structure simple and easy to map over.

When adding new images:

1. Put the image inside `public/images/`.
2. If the section uses multiple images, create or reuse its section folder.
3. Use a descriptive file name.
4. Update the appropriate root data file with the public image path.
5. Render it with `next/image` when appropriate.

When a design decision is not specified, choose the cleanest and most restrained option consistent with this document.
